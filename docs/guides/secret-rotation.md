# Secret rotation

What to do when a credential has been exposed, and the one exposure this
repository already has.

---

## The known exposure

`31fc1b5` committed a `.env` file. `73b012e` deleted it. The file is still in
the history, and this repository is public, so **every value it contained must
be treated as published** — not as "leaked briefly", not as "probably fine".
Anyone who has ever cloned this repository has them on disk.

What was in it:

| Variable | What it protects | Severity |
|---|---|---|
| `JWT_SECRET` | Signs every session token | **Critical** |
| `POSTGRES_PASSWORD` / `DB_PASSWORD` | The application database | **Critical** |
| `MINIO_ROOT_PASSWORD` | Object storage root account | High |
| `POSTGRES_USER` / `MINIO_ROOT_USER` | Usernames, not secrets | Informational |

The `JWT_SECRET` is the sharp one. Knowing it means being able to *mint* a
valid session token for any user, including an admin — no password required,
no login attempt to rate-limit, nothing in the audit log to notice. Rotating it
is not optional, and it is the first thing to do.

### Does this affect my install?

Only if you took the secret from this repository rather than generating your
own — which is exactly what the file invited, since it was labelled
"Generated by setup-docker.ps1".

Since [#13], `assertProductionSecrets()` in `backend/src/config/secrets.ts`
refuses to start in production on any of the shipped placeholder values, and
`stewardpos_secure_password_123` is one of them. So a **production** install on
the leaked database password cannot boot today. The leaked `JWT_SECRET` is a
random 32-character string rather than a recognisable placeholder, so it is
*not* in that list and would start happily. Check yours:

```bash
grep JWT_SECRET backend/.env
```

If it is `LGt59weWXY1TarNADbC6lv7xyFkqPjzR`, rotate now.

## Rotating

### 1. `JWT_SECRET`

```bash
openssl rand -base64 48
```

Put the new value in `backend/.env` and restart the API.

**Every signed-in user is signed out**, including cashiers mid-shift — the old
tokens no longer verify. Do it between shifts, or accept that everyone signs in
again. There is no rolling rotation: the app verifies against one secret, and
accepting both old and new during a window would keep the compromised one
valid, which is the thing being fixed.

### 2. Database password

```bash
openssl rand -base64 32
```

Change it in the database itself and in `backend/.env` together:

```sql
ALTER USER stewardpos_user WITH PASSWORD 'the-new-value';
```

```bash
docker compose up -d --force-recreate backend
```

If you run the bundled Compose Postgres, `POSTGRES_PASSWORD` only takes effect
on **first** initialisation of the data volume — changing it in `.env` alone
does nothing to an existing database. The `ALTER USER` above is what actually
changes it.

### 3. MinIO / S3 credentials

Only if `STORAGE_ADAPTER=s3`. Issue a new access key pair in your provider's
console (or MinIO's), update `S3_ACCESS_KEY_ID` and `S3_SECRET_ACCESS_KEY`,
restart, confirm an image still loads, then **delete the old pair**. A rotation
that leaves the old key working is not a rotation.

### 4. Payment credentials

Not part of this exposure — they live in the database, not in `.env`. But if
you have reason to think the database itself leaked, roll the Stripe/Square
keys at the provider, because `CREDENTIALS_KEY` only helps if it was set:
without it those values are stored in clear text. See
`backend/src/services/credentialCrypto.ts`.

## Removing it from the history

Rotation makes the leaked values worthless. Rewriting the history removes them
from view. **Do the rotation first** — it is what actually reduces risk, and it
does not require coordinating with anyone.

History rewriting is deliberately not automated here, and no pull request can
do it. It rewrites every commit SHA after the affected one, which means:

- every open pull request has to be rebased or reopened
- every clone has to be re-cloned or hard-reset
- every tag has to be re-pointed, and every release artefact's provenance
  changes
- GitHub keeps the old objects reachable via the API until support garbage-
  collects them, so it is **not** immediate even after a force-push

If you still want it, [`git-filter-repo`](https://github.com/newren/git-filter-repo):

```bash
git clone --mirror https://github.com/24Skater/stewardpos.git
cd stewardpos.git
git filter-repo --invert-paths --path .env
git push --force --all
git push --force --tags
```

Then open a GitHub support ticket to expire the cached objects, tell every
contributor to re-clone, and delete the `commits` entry from `.gitleaks.toml`.

## Preventing the next one

`.gitleaks.toml` and the blocking **Secret scan** job in `.github/workflows/ci.yml`
scan the full history on every pull request. A new secret fails the build
before it merges.

To catch it even earlier, locally:

```bash
docker run --rm -v "$PWD:/repo" zricethezav/gitleaks:v8.30.1 \
  protect --source=/repo --config=/repo/.gitleaks.toml --staged --redact
```

Run it from a `pre-commit` hook and the secret never leaves your machine.
