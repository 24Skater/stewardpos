# StewardPOS — Master Plan to Go‑Live

> **Audience:** engineers and AI coding agents executing this build.
> **Goal:** take StewardPOS from its current *half‑finished, AI‑scaffolded* state to a
> **fully working, self‑hostable v1.0 product** that a church or small business can run in
> production on a single VPS via Docker Compose.
>
> This plan is written to be executed **top to bottom, one phase at a time**. Every phase file
> contains numbered tasks with explicit files, steps, acceptance criteria, and verification
> commands. **If a task seems ambiguous, the answer is in [`00-conventions.md`](./00-conventions.md)
> — read it first.** Do not invent architecture; follow the locked decisions below.

---

## 0. How to use this plan (for an executing agent)

1. Read this file and [`00-conventions.md`](./00-conventions.md) in full **before writing any code**.
2. Work phases **in order**. A phase's *Entry criteria* must be green before you start it.
3. Within a phase, do tasks in listed order unless marked `[parallel-ok]`.
4. For **every** task: create a branch, implement, satisfy the *Acceptance criteria*, run the
   *Verification* block, then open a PR per [`00-conventions.md` §Git](./00-conventions.md).
5. Never mark a task done on assertion alone. **Run the verification and paste the output.**
   (See `superpowers:verification-before-completion`.)
6. If reality contradicts this plan (a file already does the thing, or a described bug is
   already fixed), **update the plan file in the same PR** and note it — do not silently diverge.

## 1. Current state (ground truth, verified 2026‑07‑08)

StewardPOS is a **full‑stack TypeScript monorepo‑ish layout** (frontend at repo root, backend in
`backend/`). It was largely generated by Lovable + iterative AI passes. A lot exists; much of it is
**inconsistent, unverified, or insecure**. Do not trust the root `README.md` / `ROADMAP.md` /
`docs/archive/*` claims of "completed" — they are aspirational.

**Frontend** (`/src`, Vite + React 18 + TypeScript + shadcn/ui + Tailwind v4)
- ~23 routed pages wired in `src/App.tsx`: `POS`, `Inventory`, `Reports`, `Settings`,
  `ServicesPos`, `Login`, `Setup`, and 15 `admin/*` pages.
- A REST client exists: `src/lib/api-client.ts` (+ `api-types.ts`, `auth-store.ts`, `auth.ts`).
- **BUT** the original offline layer is still present and still imported by pages:
  `src/lib/db.ts` (IndexedDB), `src/lib/db-operations.ts`, `src/lib/di.ts`, and
  `src/adapters/**` (client‑side db/auth/email/sms/storage adapters). The app is **half‑migrated**
  between "offline IndexedDB app" and "REST client." This is the #1 thing to fix.
- `src/pages/Index.tsx` is dead Lovable boilerplate ("Welcome to Your Blank App"); `/` routes to `POS`.

**Backend** (`/backend`, Express + TypeScript, Postgres + SQLite adapters)
- 16 route modules mounted in `backend/src/server.ts`: `auth, products, orders, customers,
  services, quotes, returns, receipts, discounts, upload, apikeys, admin, health, setup, terminal`.
- 7 payment **terminal adapters** in `backend/src/terminal/`: Stripe, Square, Clover, Verifone,
  Dejavoo, Manual + a `TerminalAdapterFactory` and `TerminalPort`.
- Migrations `001`–`007` for **both** `postgres/` and `sqlite/` (initial schema, api keys,
  returns/refunds, discounts, receipt branding, customer archive, terminal payments).
- JWT auth middleware (`auth.ts`), RBAC middleware (`authorize.ts`), error handler, request logger,
  Helmet, CORS, rate limiting, Winston logging, `seeder.ts`, `migrator.ts`.

**Infra** (already scaffolded)
- `docker-compose.yml` (postgres + MinIO + backend + frontend), `docker-compose.demo.yml`,
  root `Dockerfile` (frontend/nginx) + `backend/Dockerfile`, `nginx.conf`, `.env.example`,
  `backend/env.example`, and `environments/{dev,qa,prod}/`.
- Default ports: frontend `8081→80`, backend `3002→3001`, postgres `5435→5432`,
  MinIO `9002/9003`.

## 2. Target architecture (v1)

```
┌──────────────────────────────────────────────────────────────┐
│ Browser (register / admin)                                    │
│   React 18 + Vite + shadcn/ui + Tailwind v4                   │
│   State: TanStack Query (server state) · authStore (JWT)      │
│   Data access: ONLY src/lib/api-client.ts  (no IndexedDB)     │
└───────────────┬──────────────────────────────────────────────┘
                │ HTTPS (nginx/Caddy TLS)  ·  Bearer JWT
┌───────────────▼──────────────────────────────────────────────┐
│ Express API (backend/)                                        │
│   Helmet · CORS · rate‑limit · Zod validation                │
│   authenticate → authorize(permission) on every route        │
│   Money repriced server‑side (integer cents)                  │
│   Orders/returns wrapped in DB transactions                   │
└───────────────┬───────────────────────┬──────────────────────┘
                │                        │
      ┌─────────▼────────┐     ┌─────────▼──────────┐
      │ PostgreSQL 16    │     │ MinIO / S3         │
      │ (source of truth)│     │ (product/receipt   │
      │ org_id nullable  │     │  images, uploads)  │
      └──────────────────┘     └────────────────────┘
                │
      ┌─────────▼───────────────────────────────────┐
      │ Payment terminals (TerminalPort)             │
      │  v1 live: Manual(cash) · Stripe Terminal     │
      │  stubbed/flagged: Square·Clover·Verifone·Dejavoo │
      └──────────────────────────────────────────────┘
```

- **Postgres is the only production database.** SQLite stays **only** for zero‑dependency local dev
  and unit tests; every migration must exist in both `migrations/postgres` and `migrations/sqlite`.
- **Single‑tenant by default**, multi‑tenant‑*ready*: nullable `org_id` on all tenant‑scoped tables,
  a single seeded default org, and an org context plumbed through the API. Full multi‑tenant SaaS is
  a documented future upgrade (see [`phase-8-deploy-selfhost.md`](./phase-8-deploy-selfhost.md)).

## 3. Locked product decisions (do not re‑litigate)

| ID | Decision | Detail |
|----|----------|--------|
| **D1** | **Backend‑authoritative REST** | Remove frontend IndexedDB/DI/adapters. Every page uses `api-client.ts`. Postgres is the single source of truth. No offline mode in v1. |
| **D2** | **v1 module scope** | **In:** POS checkout, inventory/catalog, auth + RBAC, receipts, reports/exports, branding, audit log, **Returns/Refunds**, **Discounts/Promotions**. **Deferred to backlog:** Services & Quotes, full Customer CRM/loyalty, Google/OIDC SSO, SMS, offline/PWA, plugin marketplace, mobile app. |
| **D3** | **Payments** | v1 live tenders: **Cash/manual** (change + drawer) and **Stripe Terminal** (real, end‑to‑end tested). Square/Clover/Verifone/Dejavoo adapters remain compiled but **disabled behind a feature flag** and are **not** certified for v1. |
| **D4** | **Hosting** | Single‑tenant, single‑VPS **Docker Compose** is the supported go‑live path. Schema is multi‑tenant‑ready (nullable `org_id`) with a documented upgrade path. |
| **D5** | **Brand** | Product name is **StewardPOS**. Purge "Persona POS" everywhere (see C6). |
| **D6** | **Auth v1** | Local email/password (bcrypt) + JWT. No third‑party SSO in v1. |
| **D7** | **Money** | Currency computed in **integer minor units (cents)** server‑side; stored as `DECIMAL(10,2)`. Server **always** reprices; client totals are display‑only hints. |

Deferred items are catalogued in [`phase-9-golive.md` §Backlog](./phase-9-golive.md), not deleted.

### Registers and till sign-on

Locked when those features were built, after the master plan's own phases. They
lived in two implementation plans that were deleted once delivered; the plans
were step-by-step instructions with no life after execution, but these outlive
them, so they were moved here rather than lost with them. Behaviour is described
in [`guides/register-management.md`](../guides/register-management.md); this is
the part a future change has to honour.

| ID | Decision | Detail and why |
|----|----------|----------------|
| **D8** | **A location is a real entity** | Not free text on a register. Registers carry `location_id` plus a free-text `placement`, and each site's `timezone` is what decides a report's day boundary — a chain whose sites span zones cannot share one. |
| **D9** | **A register is an enrolled device** | Not a label the browser picks. Pairing codes, `register_credentials`, `registerAuth` middleware, heartbeat, and revocation that actually destroys the credential. Rejected: a selected label, which makes attribution a claim rather than a fact. |
| **D10** | **`register_number` is unique per location, not globally** | "Register 1" may exist at two sites, because that is what staff say out loud. `display_code` resolves cross-site ambiguity. |
| **D11** | **`pin_length` is a floor of six, never a fixed width** | An org may raise it to eight; it may never go below six. Validated on write in `services/pins.ts` as a field error, so the admin UI can render it against the input. |
| **D12** | **The register cap counts `pending`, `active` and `disabled` — never `retired`** | A disabled device is expected back and still holds its slot; a retired one is gone. This is what stops "we swapped a broken till" consuming a licence slot forever. A register with sales is retired, never deleted. |
| **D13** | **A till session is a server-minted JWT, bound to its shift** | `POST /api/auth/till` issues it and `authenticate` rejects it the moment the shift closes. Rejected: making `X-Register-Token` itself the credential — a stolen terminal would then hold a standing one, and every route's `req.user` would have to be derived from the shift. |
| **D14** | **Pairing is required to sign on with a PIN** | So a six-digit PIN is never the only thing in front of the shop's data, and guessing is impossible from an unenrolled browser. Assuming a till (D15) is the one deliberate, audited exception. |
| **D15** | **An assumed till attributes to the admin, never to the emulated cashier** | `POST /api/auth/till/assume` lets an admin work a register without its device token, optionally naming a cashier to emulate for display. The sales are the admin's. Gated on `registers:write`, audited, time-boxed to 30 minutes. |
| **D16** | **The password form refuses cashiers** | A user whose roles are all `standard` is turned away from `/login` and sent to the till. Admin, Supervisor and Reporter keep it. Whether a till asks for a PIN at all stays `requireSignIn`, a per-register setting an admin already owns.

## 5. Definition of "go‑live" (v1.0 acceptance)

StewardPOS v1.0 ships when **all** are true:
- A fresh `git clone` + documented steps yields a running system on a clean Ubuntu VPS via
  `docker compose up -d`, reachable over HTTPS, in under 30 minutes by following
  [`phase-8`](./phase-8-deploy-selfhost.md) docs only.
- First‑run setup wizard creates the admin + org; seeded roles/permissions work.
- A cashier can: sign in → search/scan products → build a cart → apply a discount →
  take **cash** and **Stripe Terminal** payment → complete a **transactional** sale that
  **decrements stock** → print/email a branded receipt.
- A manager can: process a **return/refund** against a receipt (with restock), manage inventory,
  view reports, export PDF/Excel/CSV, configure branding, and review the audit log.
- Every protected endpoint enforces authN + RBAC. Server reprices all money. No secrets in the repo.
- CI is green: typecheck, lint, unit/integration tests (≥80% on core money modules), e2e smoke,
  and Docker image builds all pass.
- Documentation in `docs/` covers install, configure, operate, back up, upgrade, and troubleshoot.

See the full checklist in [`phase-9-golive.md`](./phase-9-golive.md).
